# CRA-SME Toolkit v1.1 → v1.2: Improvement Recommendations

**Document type:** Technical review and implementation backlog  
**Date:** 17 October 2026  
**Baseline:** `cra-sme-toolkit-v1.1.0.zip` / Git bundle `v1.1.0`  
**Audience:** Toolkit maintainers, SME pilot partners, academic researchers, cybersecurity/compliance reviewers  
**Status:** Recommendations for development and independent verification; **not** a legal conformity opinion

## Executive summary

CRA-SME v1.1 is a useful research-oriented foundation linking product risks, software supply-chain evidence, vulnerability data and CRA documentation. Its next release should prioritize **reliable release decisions and evidence quality** over further dashboard features. The core research opportunity is a reproducible, product-specific **obligation → risk → control → test → evidence → reviewer decision** chain that remains valid through product changes.

**Recommended order:** (1) eliminate false-green scan states; (2) unify release gates and applicable mandatory CRA obligations; (3) validate legal mappings and product applicability; (4) bind evidence to product/build and measure freshness; (5) strengthen risk-model and SME pilot validation.

> **Legal caution:** The CRA is Regulation (EU) 2024/2847. Article 14 reporting duties began applying on **11 September 2026**; the main product requirements apply from **11 December 2027**. Product classification, exclusions, conformity assessment routes, support periods and reporting decisions require verification against the consolidated law and up-to-date official guidance. A numeric risk score or a successful CI run is **not** proof of conformity.

## 2. P0 implementation specifications

### P0-01 — Fail safely on unavailable security evidence

**Observed issue in uploaded v1.1 workflow:** `automation/security-scan.v1.1.yml` uses `continue-on-error: true`, `|| true`, and a KEV feed fallback to `{"vulnerabilities":[]}`. This can obscure scan failures or network problems. The default `GATE_ENFORCE: "false"` also means the demonstration pipeline is not an enforcing production release gate.

**Change:** Record `tool`, `version`, `execution_status`, `started_at`, `finished_at`, `input_digest`, `output_digest`, `finding_count` and `error_code` for each required scan. Make the gate depend on status **and** findings.

```text
PASS            all required checks completed, no applicable blocking findings,
                required obligation evidence verified, approval gate satisfied
FAIL            known security/compliance blocker detected
REVIEW_REQUIRED scan/feed/evidence incomplete, ambiguous or human determination needed
```

**Test scenarios:** unavailable KEV feed; scanner process non-zero; missing OSV JSON; malformed Trivy JSON; empty SBOM due to generator failure; wrong product hash; expired evidence; known exploited affected component with unknown reachability. **Do not** automatically approve these as clean.

**Implementation caution:** Not every scanner exit code indicates a tool failure (some indicate findings). Normalize documented exit codes separately from execution errors. A temporary feed problem does not, by itself, prove a product violates the CRA; it prevents a confident automated approval.

### P0-02 — Single release decision engine

Use one gate rather than independent scripts reporting overlapping statuses.

**Inputs:** `product.json`, applicable-obligations catalogue, threat/risk register, SBOM, scanner manifests, evidence links, approved exceptions, conformity-route decision and reviewer sign-offs.

**Outputs:** signed/versioned JSON decision plus human-readable report. Suggested output fields:

```json
{
  "schema_version": "1.0",
  "product_id": "DEMO-001",
  "product_version": "1.2.0",
  "build_sha": "REPLACE_WITH_REAL_BUILD_SHA",
  "decision": "REVIEW_REQUIRED",
  "reasons": ["SCAN_EVIDENCE_MISSING", "LEGAL_MAPPING_REVIEW_PENDING"],
  "mandatory_obligations_checked": 0,
  "evidence_manifest_digest": "REPLACE_WITH_HASH",
  "reviewer": null,
  "timestamp_utc": "REPLACE_AT_RUNTIME"
}
```

**Key rule:** separate `technically eligible for human conformity review` from `legally conformant`. The system cannot itself issue a lawful conformity declaration or decide borderline legal applicability without appropriate human review.

**Acceptance tests:** missing mandatory mapping cannot become PASS due to low risk score; expired approval changes status; non-applicable obligation requires documented rationale; corrections re-run only necessary checks without losing audit history.

### P0-03 — Legal requirements catalogue QA

For each obligation, store:

- Unique ID and exact regulation article/annex reference.
- Verbatim-short requirement description or carefully reviewed summary.
- Manufacturer/importer/distributor applicability and product-category condition.
- Effective date and transition rules where relevant.
- Conformity assessment pathway dependencies; standard/common specification where applicable.
- Required evidence artifact, evidence owner, verifier and verification date.
- Official URL, source version, reviewer and `verified/unverified/superseded` status.

**Review workflow:** legal reviewer validates references; technical reviewer maps testable aspects; product owner confirms applicability. Distinguish a statutory requirement, a standard-based implementation option and a recommended internal practice.

### P0-04 — Evidence lineage and freshness

Every artifact should reference the actual build under assessment, for example:

```text
Product ID -> release version -> build SHA / image digest
  -> SBOM digest -> scanner inputs & outputs -> vulnerability triage
  -> applicable CRA obligations -> controls/tests -> human review
```

Add checks for stale test results, outdated SBOM, changed dependency lockfile, altered firmware binary, revoked sign-off, modified product use, and missing product/build identifiers. Define configurable evidence freshness rules; **do not invent a legal freshness interval** where the CRA does not specify one.

## 3. Risk model improvement plan

**Keep the simple scoring model** `L × I × E` as an educational or prioritization baseline only. Ordinal scale multiplication has mathematical limitations and must not be presented as a probability or statutory CRA metric.

1. **Define anchors** for Likelihood, Impact and Exposure (levels 1–5), including what constitutes credible evidence for each rating.
2. **Record uncertainty** using `low / central / high` assumptions and justification rather than false numerical precision.
3. **Separate dimensions**: probability of exploitation, consequences for users/safety/operations, exposure, vulnerability maturity, and existing mitigations.
4. **Estimate financial loss** only when defensible: incident frequency and loss-magnitude distributions, sensitivity analysis and optional Monte Carlo simulation. Label estimates as illustrative if based on assumptions.
5. **Handle non-negotiable controls independently**: a low risk score does not waive Annex I security requirements, support obligations or mandatory reporting.
6. **Measure agreement** between assessors, stability of priority lists and effort to complete assessments.

**Recommended research comparison:** baseline ordinal model vs anchored expert model vs probabilistic risk model. Primary outcomes: agreement, ranking stability, calibration where ground truth exists, time/cost and decision quality.

| `product-classification.md` | product category, class, intended use, evidence, conformity route, legal review |
| `support-period-decision.md` | expected use, support period, justification, updates contact, management approval |
| `security-update-plan.md` | supported versions, authenticity, release channels, patch workflow, notices |
| `substantial-modification-log.csv` | changed feature, changed risks, impact on assessment, decision, approver |
| `vulnerability-disclosure-policy.md` | intake, security contact, triage, acknowledgement, coordination, confidentiality |
| `article14-reporting-record.md` | awareness timestamp, reportability rationale, deadlines, platform receipt, follow-ups |
| `technical-file-index.md` | Annex VII section, evidence location, version, owner, reviewer, status |
| `eu-declaration-checklist.md` | required declaration fields and signatory review, no pre-signed sample |
| `release-approval.md` | product/build, unresolved findings, legal decisions, reviewer, final release outcome |

For Article 14, distinguish **actively exploited vulnerabilities** and **severe security incidents impacting the security of the product**. Record applicable early warning (24h), follow-up (72h), and final reporting milestones without assuming that every vulnerability or every incident is automatically reportable. Verify reporting details against current official instructions before deployment.

## 5. Research and experimental strengthening

### Research focus

**Suggested article title:** *From Cybersecurity Risk to Compliance Evidence: Design and Evaluation of a Traceable Cyber Resilience Act Implementation Framework for SMEs*.

**Core research question:** Can product/build-bound, machine-verifiable risk-to-evidence traceability reduce missing or stale CRA compliance evidence and improve release-review efficiency compared with manual SME practice?

### Three coherent research pillars

**Pillar A — Evidence traceability:** Experiments E4 and E7; measure coverage, integrity, freshness detection, false-green decisions, reviewer time and explainability. Compare manual spreadsheet/record-based handling with CRA-SME.

**Pillar B — Risk assessment validity:** E3 supported by E1/E2; evaluate assessment reliability, prioritization consistency, SBOM coverage and vulnerability matching. Include ground truth and realistic perturbations, not only synthetic examples.

**Pillar C — SME utility:** E5/E6/E8; compare baseline and assisted workflows on task completion time, cost, reporting preparedness, perceived usability and documentation quality. Stratify by SME size and product class.

### Evaluation design and reporting

- Pre-register hypotheses, primary outcomes and analysis plan before pilot data collection.
- Include a traceable set of deliberately seeded faults and stale/mislinked artifacts.
- Randomize or counterbalance assessors and scenarios when feasible; adjust analysis for participant and scenario effects.
- State effect sizes and uncertainty intervals, not only p-values.
- Report human verification time and implementation/hosting overhead alongside automation gains.
- Distinguish synthetic, lab-based and real SME data; avoid claiming conformity was established merely through toolkit use.
- Publish sanitized benchmark inputs, configuration, expected outputs, test fixtures and reproducibility instructions.
- Obtain appropriate participant consent and define confidential-data handling for industry studies.

### Proposed measurable metrics

| Metric | Operational definition |
|---|---|
| Evidence completeness | Verified applicable obligation–evidence links / applicable obligations |
| Evidence freshness recall | Correctly identified stale links / seeded stale links |
| False-green rate | Incorrect PASS decisions / cases with planted release blockers |
| Reviewer time | Minutes spent checking a standardized product evidence package |
| Scan availability | Successful required scanner executions / scheduled executions |
| Reporting preparedness | Correct decisions and deadlines in scripted tabletop scenarios |
| Risk agreement | Ordinal inter-rater agreement and ranking stability across assessors |
| SME effort | Initial setup hours + hours per release + maintenance hours/month |

## 7. Suggested release gates

### v1.2 minimum release gate (recommended)

- [ ] All P0 issues resolved with negative tests.
- [ ] All security tool failures produce explicit status and cannot create false-green output.
- [ ] No required compliance mapping silently defaults to applicable/compliant.
- [ ] Build and evidence digests validated.
- [ ] Official CRA citation and catalogue legal QA completed for the intended pilot scope.
- [ ] Reportability playbook distinguishes the major Article 14 cases and dates.
- [ ] README explicitly differentiates automated evidence from legal conformity.
- [ ] Clean-install CI and sample workflow tested; no placeholder release contacts remain.

### v1.3 research validation gate

- [ ] Full benchmark with labelled ground truth, scanner versions and limitations.
- [ ] Traceability mutation tests and false-green-rate results.
- [ ] Risk reliability experiments and analysis scripts.
- [ ] Reproducible notebooks with sanitized sample outputs.

### v2.0 external SME pilot gate

- [ ] Independent security and legal review of intended product scopes.
- [ ] SME recruitment, consent, confidential data management and ethics review as appropriate.
- [ ] Baseline vs toolkit-assisted comparison performed and documented.
- [ ] Costs, usability, failure modes and generalizability limits reported.

## 8. Recommended next development sequence

**Sprint 1 — Reliability:** P0-01, P0-02; implement explicit states, fail-safe error handling, negative CI tests.

**Sprint 2 — Regulatory traceability:** P0-03, P0-04; legally checked catalogue plus validated build-bound evidence provenance.

**Sprint 3 — SME operations:** P1-02, P1-03, P1-05; reporting, support/update and documentation workflows.

**Sprint 4 — Reproducibility and methods:** P1-01, P1-04, P2 issues; execute notebooks, finalize risk-model comparison and evaluation protocols.

**Priority principle:** Ship a smaller, dependable traceability/release-review mechanism before adding a larger dashboard or AI-generated compliance verdict. Human accountability and reproducibility are part of the research contribution.
